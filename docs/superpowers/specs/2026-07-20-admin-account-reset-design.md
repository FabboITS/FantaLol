# Administrator Account Reset Design

## Goal

Permanently remove every existing account and all user-owned data, replace the legacy administrator with `Natsu_Admin`, invalidate all previously issued login tokens, and ensure the login interface and maintained project artifacts never reveal administrator credentials.

## One-Time Reset

A dedicated transactional initializer runs during application startup. It uses the presence of the legacy `admin` account as the one-time migration marker.

When the legacy account exists, the initializer:

1. Deletes all leagues, allowing their cascades to remove auctions, rosters, matchdays, statistics, and formations.
2. Deletes all remaining user-owned teams and profiles through the existing entity relationships.
3. Deletes every user, including all regular and administrator accounts.
4. Creates `Natsu_Admin` as the sole enabled account with role `ADMIN`.

All steps execute in one database transaction. A failure rolls the reset back instead of leaving a partially deleted database.

After a successful reset, later startups do not repeat the deletion because the legacy account no longer exists. Users who register after migration therefore survive restarts. On a fresh database, the normal seed flow creates `Natsu_Admin` directly.

## Credential Storage

The administrator password is represented in maintained project files only by a precomputed BCrypt hash. The requested plaintext password must not appear in Java source, frontend files, configuration defaults, SQL seed files, README content, Postman examples, logs, or API responses.

The initializer reconciles the administrator account only as part of initial creation or the legacy reset. It does not overwrite the password on every restart.

## Session Invalidation

The application uses stateless JWTs rather than server-side sessions. Deleting every existing user invalidates all previously issued tokens because token validation reloads the token subject from the database.

The JWT filter will treat a token for a deleted user, or an otherwise malformed/invalid token, as unauthenticated. Protected endpoints return `401 Unauthorized` instead of leaking an exception or returning a server error. The existing frontend API behavior clears stale local authentication state after an unauthorized protected request.

## Login Interface and Published Artifacts

The `Accedi` dialog keeps blank username and password fields and contains no demo credential hint, preset value, or administrator-specific placeholder. Browser password-manager behavior is not controlled by the application, but the application itself never supplies credentials.

Legacy administrator credentials are removed from maintained frontend HTML, README documentation, Postman requests, and SQL seed comments/data. Generated `target` output is not edited directly; it is regenerated by the build.

The existing `Ctrl+Y` directory remains role-protected and continues to show only regular usernames. It never returns or renders passwords, hashes, emails, IDs, or profiles.

## Verification

Automated tests will establish that:

- A legacy installation is reset transactionally to exactly one `Natsu_Admin` account.
- Legacy regular accounts and their associated league data are removed.
- Running initialization again preserves users created after migration.
- Fresh initialization creates the new administrator.
- The stored administrator credential is BCrypt, not plaintext.
- Tokens for removed users receive `401 Unauthorized`.
- Static login resources contain neither the old credentials nor a demo administrator hint.
- Existing authentication and administrator-directory authorization tests remain green.

Repository-wide scans will confirm that the old maintained credentials and the new plaintext password are absent outside ignored/generated build output and this specification's required username references.
